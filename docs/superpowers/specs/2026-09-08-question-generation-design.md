# 질문 생성 시스템 설계

- 작성일: 2026-09-08
- 대상: 퀴즈 앱의 질문 공급 파이프라인

## 1. 배경과 목표

### 앱의 게임 구조

초대된 친구들끼리 하나의 질문에 각자 답을 적고, **전원이 제출을 완료했을 때에만** 서로의 답을 볼 수 있다. 정답을 맞히는 게임이 아니라, 서로의 생각이 얼마나 다른지 확인하는 게임이다.

### 이 시스템이 해결할 것

질문을 카테고리별로 확장해야 하는데, 사람이 계속 쓰는 건 지속 불가능하다. LLM으로 생성하되 **품질이 유지되는 파이프라인**을 만든다.

### 기준 질문

> "만약에 네가 시각장애인이면, 변을 보고 나서 닦을 때 다 닦였는지 아닌지 확인을 어떻게 하지?"

이 질문이 잘 작동하는 이유를 분해하면 생성 기준이 나온다.

| 성질 | 내용 |
|---|---|
| 경험 불가능성 | 대부분의 사람이 겪어본 적 없는 상황 |
| 일상 구체성 | 상황 자체는 극도로 일상적이고 구체적. 추상적 철학이 아님 |
| 답은 존재함 | 실제 방법이 있는데 아무도 모름. 그래서 추측이 갈림 |
| 약한 금기 | 웃기고, 혼자 검색하긴 민망함. 같이 까보는 게 재밌음 |
| 성향 노출 | 실용적으로 답할지 웃기게 답할지가 사람마다 다름 |

핵심 공식: **일상 행위 x 그것을 불가능하게 만드는 제약**

### 설계 원칙

1. **창의성을 LLM에 맡기지 않는다.** "재밌는 질문 만들어줘"는 실패한다. 탐색 공간은 코드가 통제하고, LLM은 조합을 문장으로 다듬는 역할만 한다.
2. **앱은 LLM을 호출하지 않는다.** 모든 생성은 오프라인 배치. 앱은 완성된 풀에서 꺼내 쓰기만 한다.
3. **실사용 데이터를 생성기로 되돌린다.** 전원 답변 구조 덕분에 답변 데이터가 자동으로 쌓인다. 이걸 품질 신호로 쓴다.

## 2. 파이프라인 개요

```
[1] 시드 조합 생성       코드가 축 테이블에서 미사용 조합을 뽑음
        |
[2] 생성                형식별 프롬프트, 배치 20개씩, temperature 1.0
        |
[3] 중복 제거           임베딩 유사도 컷 + 시드 해시 중복 컷
        |
[4] 심사                LLM judge 루브릭 스코어링
        |
[5] 안전 필터           judge와 분리된 별도 패스
        |
[6] 사람 검수 큐        승인 / 반려 / 수정
        |
[7] 질문 풀 (DB)        형식 + 소재 태그 + 점수
        |
[8] 앱 서빙
        |
[9] 실사용 신호 수집 ---> [2]의 few-shot으로 환류
```

각 단계는 독립적으로 실행 가능하고 각자 자기 입출력 테이블만 안다. 한 단계가 실패해도 앞 단계 결과는 DB에 남아 재시도 가능하다.

## 3. 카테고리 축의 이중 구조

카테고리를 두 층으로 분리한다.

- **형식(format)** — 생성기 내부 구조. 유저에게 보이지 않음.
- **소재(topic)** — 유저에게 보여줄 라벨. 태그로 부착.

형식마다 생성 프롬프트가 근본적으로 다르기 때문에 분리가 필요하다. 제약형은 "제약 리스트와 행위 리스트를 조합"이고 선택형은 "동등하게 괴로운 두 선택지 뽑기"라서, 하나의 만능 프롬프트로는 둘 다 뽑을 수 없다.

반면 유저에게 "제약형 질문 하실래요?"는 의미가 통하지 않는다. 유저는 "오늘은 연애 편"을 원한다.

### 형식 4종

| format | 축 구조 | 예시 |
|---|---|---|
| `constraint` (제약형) | 제약 x 일상행위 | 시각장애인은 변 닦고 다 닦였는지 어떻게 확인할까? |
| `dilemma` (선택형) | 동등하게 괴로운 두 선택지 | 평생 남의 속마음이 들림 vs 내 속마음이 다 들림 |
| `projection` (예측형) | 상황 x "너라면" | 내일 지구가 끝나면 오늘 밤 누구한테 전화하나? |
| `confession` (폭로형) | 사회적 금기 영역 | 부모님한테 끝까지 숨긴 것 하나만 |

### 소재 태그

생성된 질문에 LLM이 스스로 붙이고, 사람 검수 단계에서 교정한다.

```
신체생리 / 연애 / 가족 / 죽음 / 돈 / 일직업 / 친구관계 /
음식 / 사회적금기 / 비현실상황
```

한 질문에 복수 태그 허용. 유저 UI는 이 태그로 필터링한다.

## 4. 시드 축 테이블

### constraint (제약형)

```
제약 (constraint_axis)
  시각장애 / 청각장애 / 손이 하나뿐 / 말을 못 함 /
  기억이 10분만 유지됨 / 무중력 상태 / 물이 전혀 없음 /
  남들이 내 생각을 들을 수 있음 / 몸이 30cm로 작아짐 /
  거짓말을 할 수 없음

행위 (activity_axis)
  배변 후 뒤처리 / 샤워 / 라면 끓이기 / 이별 통보 /
  지하철 타기 / 소개팅 / 장례식 참석 / 면접 / 병원 진료
```

10 x 9 = 90개 시드 조합. 시드당 변형 3개 요청 = 후보 270개.

### dilemma (선택형)

```
괴로움 축 (misery_axis)
  프라이버시 상실 / 신체 불편 / 사회적 평판 / 시간 낭비 /
  관계 단절 / 감각 상실 / 자유 제한

강도 (intensity)
  평생 / 1년 / 하루에 1시간
```

두 개의 서로 다른 괴로움 축을 짝지어 시드를 만든다. 7C2 x 3 = 63개 시드.

### projection (예측형)

```
상황 축 (scenario_axis)
  시한부 통보 / 로또 당첨 / 무인도 표류 / 시간여행 /
  투명인간 / 과거로 편지 / 다른 사람 몸

제한 축 (limit_axis)
  딱 하나만 / 딱 한 명만 / 24시간 안에 / 아무도 모르게
```

7 x 4 = 28개 시드.

### confession (폭로형)

```
금기 영역 (taboo_axis)
  거짓말 / 질투 / 돈 / 성적 취향 / 가족에 대한 감정 /
  친구에 대한 속마음 / 후회 / 몰래 한 행동
```

8개 시드. 시드당 변형을 많이 뽑는다 (10개).

### 조합 관리

각 시드 조합에 `seed_hash`를 부여한다.

```
seed_hash = sha256(format + ":" + sorted(axis_values).join("|"))[:16]
```

배치 실행 시 이미 사용된 `seed_hash`를 제외하고 뽑는다. 축에 값을 하나 추가하면 새 조합이 자동으로 생긴다. 카테고리 확장 = 축 테이블에 행 추가.

## 5. 생성 프롬프트

### 공통 규칙

1. **한 번에 20개 배치로 요청.** 개별 호출은 비효율적이다. judge가 어차피 대부분 거르므로 많이 뽑고 많이 버린다.
2. **골든 예시 3~5개를 매 호출마다 랜덤 샘플링.** 예시를 고정하면 출력이 예시에 수렴한다 (mode collapse).
3. **temperature 1.0.** 다양성이 목적이고 품질은 judge가 담당한다.
4. **출력은 JSON 배열.** 파싱 실패 시 해당 배치만 재시도한다.

### constraint 프롬프트 (초안)

시스템:

```
너는 친구들끼리 하는 대화형 게임의 질문을 만든다.
이 게임은 모두가 각자 답을 적고, 전원이 제출한 뒤에 서로의 답을 동시에 공개한다.
정답을 맞히는 게임이 아니라 서로 얼마나 다르게 생각하는지 보는 게임이다.

[좋은 질문의 조건]
- 상황이 구체적이고 일상적이다. 추상적 철학 질문이 아니다.
- 실제로 답이 존재하지만 대부분의 사람은 모른다. 그래서 각자 추측이 갈린다.
- 전문 지식 없이 누구나 자기 생각을 말할 수 있다.
- 남이 뭐라고 답했는지 궁금해진다.
- 혼자 검색하긴 좀 민망하지만 같이 얘기하면 재밌다.

[반드시 피할 것]
- 정답이 뻔해서 모두 같은 답을 할 질문
- "만약 하늘이 초록색이라면" 같은 밍밍한 가정
- 전문 지식이 있어야 답할 수 있는 질문
- 특정 집단을 조롱하거나 비하하는 질문

[안전 기준 - 가장 중요]
어떤 조건이나 장애를 다룰 때, 그 사람의 "삶의 방식"이 궁금한 것은 괜찮다.
그 사람의 "결함"을 웃음거리로 삼는 것은 안 된다.

판정 테스트: 그 당사자가 이 질문을 봤을 때, 기분 나빠하지 않고
             오히려 같이 답할 수 있는가?

- 통과: "시각장애인은 변 닦고 다 닦였는지 어떻게 확인할까?"
        (당사자가 답하면 오히려 제일 좋은 답이 나온다)
- 탈락: "시각장애인은 얼마나 불편할까?"
        (답이 아니라 동정을 요구한다)

[예시]
{golden_examples}

[출력 형식]
JSON 배열만 출력한다. 다른 텍스트는 쓰지 않는다.
[
  {
    "text": "질문 문장 (한국어, 반말, 물음표로 끝남)",
    "topic_tags": ["신체생리"],
    "seed_hash": "입력으로 받은 시드의 해시"
  }
]
```

유저:

```
아래 조합들을 각각 질문 문장으로 만들어라.
조합 하나당 서로 다른 각도로 3개씩 만든다.

1. [seed_hash: a1b2c3d4] 제약: 시각장애 / 행위: 배변 후 뒤처리
2. [seed_hash: e5f6g7h8] 제약: 기억이 10분만 유지됨 / 행위: 소개팅
...
```

### 나머지 형식

같은 시스템 프롬프트 골격을 쓰되 `[좋은 질문의 조건]`과 유저 메시지의 조합 제시 방식을 형식에 맞게 바꾼다.

- `dilemma`: "두 선택지가 **동등하게** 괴로워야 한다. 한쪽이 명백히 나으면 실패다."를 추가
- `projection`: "상황을 겪는 주인공이 답변자 본인이어야 한다"를 추가
- `confession`: "답하기 부담스럽지만 답할 수는 있는 선을 지킨다. 대답 자체가 불가능한 수위는 안 된다"를 추가

## 6. 중복 제거

두 단계로 거른다.

1. **시드 해시 중복** — 이미 사용된 조합은 배치 진입 전에 제외
2. **임베딩 유사도** — 생성된 질문을 임베딩해서 기존 풀 및 같은 배치 내 질문과 비교. 코사인 유사도 **0.85 초과**면 탈락

같은 배치 안의 중복은 점수가 높은 쪽을 남긴다 (judge 이후 처리).

## 7. 심사 (LLM judge)

생성기와 **별도 호출**로 진행한다. 자기가 만든 걸 자기가 심사하면 후하게 준다.

### 루브릭

각 항목 0~5점.

| 항목 | 판정 질문 |
|---|---|
| `variance` (답변 분산도) | 10명이 답하면 서로 다르게 답할까? 정답이 뻔하면 0점 |
| `accessibility` (접근성) | 전문 지식 없이 누구나 답할 수 있나? |
| `concreteness` (구체성) | 상황이 구체적인가, 추상적 철학인가? |
| `curiosity` (궁금증) | 남의 답이 궁금해지나? |

**`variance`가 사실상 이 앱의 핵심 지표다.** 전원이 답해야 공개되는 게임인데 답이 다 똑같으면 공개되는 순간이 재미없다.

### 합격선

```
안전 필터 통과 (필수)
AND 4개 항목 평균 >= 3.5
AND variance >= 3 (개별 하한)
```

### judge 출력

```json
{
  "variance": 4,
  "accessibility": 5,
  "concreteness": 5,
  "curiosity": 4,
  "reason": "각자 다른 방법을 떠올릴 여지가 크고 상황이 구체적임"
}
```

`reason`은 사람 검수 큐에서 판단 근거로 노출한다.

## 8. 안전 필터

judge와 분리된 독립 패스로 돌린다. 점수가 아니라 **통과/탈락 이진 판정**이다.

### 판정 기준

```
[통과 조건]
그 사람의 "삶의 방식"에 대한 진지한 호기심인가?

[탈락 조건]
- 그 사람의 "결함"을 웃음거리로 삼는가?
- 답변이 아니라 동정을 요구하는가?
- 특정 집단에 대한 고정관념을 전제로 하는가?
- 실존 인물을 지목하는가?
- 미성년자 관련 성적 내용, 자해 조장, 범죄 방법을 다루는가?

[최종 테스트]
그 질문의 당사자가 이 게임에 참여했을 때,
기분 나빠하지 않고 같이 답할 수 있는가?
```

### 탈락 처리

`status = rejected`로 두고 삭제하지 않는다. 탈락 사유를 모아 생성 프롬프트의 `[반드시 피할 것]`을 주기적으로 보강한다.

## 9. 사람 검수

### 초기 정책

**전량 사람 검수.** judge를 통과한 질문도 사람이 승인해야 `live`가 된다.

검수 화면에서 볼 것:
- 질문 문장
- judge 점수 4종 + reason
- 소재 태그 (수정 가능)
- 질문 문장 (수정 가능 — 사소한 어색함은 고쳐서 승인)

검수 우선순위 축은 **안전**이다. judge가 통과시켰어도 사람 눈에 걸리면 반려한다.

### 자동 승인 전환

사람이 승인한 질문(`approved` 또는 `live`)이 **100개**를 넘어가면 자동 승인을 도입한다.
(10번 섹션의 `golden`은 실사용 30회 이상이 조건이라 초기에는 도달할 수 없다. 자동 승인 전환의 기준은 `golden`이 아니라 누적 승인 수다.)

```
judge 평균 >= 4.5 AND 안전 통과 AND 최대 유사도 < 0.7  ->  자동 승인
그 외                                                  ->  사람 검수 큐
```

유사도 임계값이 두 개인 이유: 6번의 **0.85**는 "중복이라 버린다"는 탈락선이고, 여기의 **0.7**은 "충분히 새로워서 사람 눈 없이 통과시킨다"는 더 엄격한 신뢰선이다. 0.7~0.85 구간은 버리지는 않되 사람 검수로 보낸다.

자동 승인분은 사후 샘플링 검수(주 1회, 10%)로 감시한다.

### 상태 전이

```
pending --(judge+안전 통과, 사람 승인)--> approved --(배포)--> live
pending --(안전 탈락 또는 사람 반려)--> rejected
live    --(실사용 성과 미달)--> retired
```

`approved`와 `live`를 나누는 이유는 배포 시점을 통제하기 위해서다. 승인된 질문을 모아두었다가 형식/소재 균형을 맞춰 한 번에 `live`로 올린다. 라이브 질문이 부족하면 `approved`에서 즉시 보충한다.

## 10. 피드백 루프

전원 답변 구조 덕분에 답변 데이터가 자동으로 쌓인다. 이게 이 앱의 해자다.

### 수집 신호

| 신호 | 계산 | 의미 |
|---|---|---|
| `answer_variance` | 답변 임베딩들의 평균 pairwise 코사인 거리 | 크면 좋은 질문 (의견이 갈림) |
| `avg_answer_len` | 답변 글자수 평균 | 길면 몰입한 것 |
| `skip_rate` | 스킵 / 서빙 | 높으면 불쾌하거나 이해가 안 됨 |
| `completion_rate` | 전원 답변 도달 / 서빙 | 방이 끝까지 간 비율 |

### 골든셋 자동 승격

```
서빙 30회 이상
AND answer_variance 상위 20%
AND skip_rate < 0.1
AND completion_rate > 0.7
  -> golden = true
```

골든으로 승격된 질문은 다음 배치의 few-shot 랜덤 샘플링 풀에 들어간다. **배치를 돌릴수록 생성 품질이 올라가는 구조**다.

### 자동 은퇴

```
서빙 30회 이상
AND (answer_variance 하위 10% OR skip_rate > 0.3)
  -> status = retired
```

## 11. 데이터 모델

```sql
-- 시드 축 값
CREATE TABLE seed_axes (
  id          BIGSERIAL PRIMARY KEY,
  format      TEXT NOT NULL,          -- constraint | dilemma | projection | confession
  axis_name   TEXT NOT NULL,          -- constraint_axis | activity_axis | ...
  value       TEXT NOT NULL,
  active      BOOLEAN NOT NULL DEFAULT TRUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (format, axis_name, value)
);

-- 사용된 시드 조합
CREATE TABLE seed_combinations (
  seed_hash   TEXT PRIMARY KEY,       -- sha256(format:sorted(values))[:16]
  format      TEXT NOT NULL,
  axis_values JSONB NOT NULL,         -- {"constraint_axis": "시각장애", "activity_axis": "배변 후 뒤처리"}
  used_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 질문 풀
CREATE TABLE questions (
  id            BIGSERIAL PRIMARY KEY,
  text          TEXT NOT NULL,
  format        TEXT NOT NULL,
  topic_tags    TEXT[] NOT NULL DEFAULT '{}',
  seed_hash     TEXT REFERENCES seed_combinations(seed_hash),
  embedding     VECTOR(1536),
  judge_scores  JSONB,                -- {variance, accessibility, concreteness, curiosity, reason}
  safety_passed BOOLEAN,
  safety_reason TEXT,
  status        TEXT NOT NULL DEFAULT 'pending',
                -- pending   생성됨, 심사 또는 사람 검수 대기
                -- approved  승인됨, 서빙 대기 (풀에 있으나 아직 배포 안 함)
                -- live      서빙 대상
                -- rejected  안전 필터 또는 사람이 반려
                -- retired   실사용 성과 미달로 은퇴
  golden        BOOLEAN NOT NULL DEFAULT FALSE,
  batch_id      TEXT,
  reviewed_by   TEXT,
  reviewed_at   TIMESTAMPTZ,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX ON questions (status, format);
CREATE INDEX ON questions USING GIN (topic_tags);

-- 실사용 통계
CREATE TABLE question_stats (
  question_id      BIGINT PRIMARY KEY REFERENCES questions(id),
  served           INT NOT NULL DEFAULT 0,
  completed        INT NOT NULL DEFAULT 0,
  skipped          INT NOT NULL DEFAULT 0,
  answer_variance  REAL,
  avg_answer_len   REAL,
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 배치 실행 기록
CREATE TABLE generation_batches (
  id           TEXT PRIMARY KEY,
  format       TEXT NOT NULL,
  seed_count   INT NOT NULL,
  generated    INT NOT NULL DEFAULT 0,
  deduped      INT NOT NULL DEFAULT 0,
  judge_passed INT NOT NULL DEFAULT 0,
  safety_passed INT NOT NULL DEFAULT 0,
  started_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at  TIMESTAMPTZ,
  error        TEXT
);
```

## 12. 부트스트랩

골든셋 없이는 생성을 시작할 수 없다. few-shot에 넣을 예시가 필요하기 때문이다.

### 순서

1. **사람이 직접 20개 작성** — 형식당 5개. 기준 질문(시각장애인 뒤처리)이 constraint의 1번.
2. 이 20개를 `golden = true`, `status = live`로 seed
3. 시드 축 테이블을 위 4번 섹션대로 채움
4. 형식별로 첫 배치 실행 (constraint부터)
5. 전량 사람 검수
6. 승인분이 100개 넘어가면 자동 승인 도입 (9번 섹션)

### 첫 배치 예상 수율

```
constraint 기준
  시드 90개 x 변형 3개 = 후보 270개
  중복 제거 후          ~ 200개
  judge 통과 (평균 3.5+) ~ 60개
  안전 통과              ~ 55개
  사람 승인              ~ 40개
```

배치 1회에 형식당 30~40개면 충분하다. 초기 목표는 형식 4종 x 40개 = **160개 라이브 질문**.

## 13. 테스트 전략

| 대상 | 방법 |
|---|---|
| 시드 조합 생성 | 축 값 개수 대비 조합 수, 중복 미발생, 미사용 조합만 반환 |
| 시드 해시 | 축 값 순서가 달라도 같은 해시 (정렬 후 해싱) |
| 생성 응답 파싱 | 잘린 JSON / 코드펜스 감싸진 JSON / 빈 배열 처리 |
| 중복 제거 | 유사도 0.85 경계값, 같은 배치 내 중복 시 고득점 선택 |
| judge 파싱 | 점수 범위 벗어남, 필드 누락 시 처리 |
| 합격선 로직 | 평균은 넘지만 variance 하한 미달 케이스 |
| 안전 필터 | 통과/탈락 골든 케이스 각 10개로 회귀 테스트 |
| 통계 집계 | answer_variance 계산, 답변 1개일 때 0 나누기 |
| 골든 승격/은퇴 | 경계 조건 (서빙 29회 vs 30회) |

**안전 필터 회귀 테스트가 가장 중요하다.** 통과해야 하는 질문 10개와 탈락해야 하는 질문 10개를 고정해두고, 프롬프트를 수정할 때마다 돌린다.

## 14. 에러 처리

| 상황 | 처리 |
|---|---|
| LLM 응답이 JSON이 아님 | 해당 배치 1회 재시도, 재실패 시 배치 실패 기록 후 다음 배치 진행 |
| LLM API 실패 | 지수 백오프 3회, 실패 시 `generation_batches.error`에 기록 |
| 임베딩 API 실패 | 중복 제거를 건너뛰고 `pending`으로 넣되 사람 검수 필수 표시 |
| judge 점수 필드 누락 | 해당 질문만 `pending` + 사람 검수 큐 |
| 미사용 시드 고갈 | 배치 중단하고 축 테이블 확장 필요 알림 |
| 라이브 질문 부족 | 은퇴 정지 + 배치 실행 알림 |
